# 功能结构设计（高校考场编排与监考分配系统 v8）

> 2026-11-02。指导教师认为「健身 / 健康管理」类题材重复度高，本项目更换题材为**高校考场编排与监考分配**。
>
> 前七版（生活数据、三角色管理平台、健身、社交化）全部作废，仅保留其框架层代码。本文件是新领域的完整设计口径。
>
> **技术核心是排考算法，不是增删改查**——这是它与前几版「管理系统」的根本区别。

## 1. 选题定位

高校期末考试周的排考，本质是一个**多约束组合优化问题**：把「考试」安排到「时段 × 教室」，再把「监考教师」匹配到每一场，同时满足学生不冲突、教室容量、教师回避、监考均衡等一堆条件。

教务人员目前的实际做法是 Excel 加人工经验：300 门课排一次要一周，冲突靠事后核对，出了差错只能局部返工，而且没法回答「这个方案比上一个好在哪」。

系统要解决三件事：

| 问题 | 现状 | 系统做法 |
|---|---|---|
| 约束多且互相牵制 | 人工只能顾住最显眼的几条（如学生不冲突），回避与负载均衡常被忽略 | 显式建模硬约束与软约束，逐条校验并定位 |
| 手工排不动 | 规模一大就靠局部返工，越改越乱 | 分阶段求解：着色 → 装箱 → 匹配 → 局部搜索 |
| 无从评价优劣 | 排完就发，没有质量指标 | 定义冲突数、软成本、工作量标准差、教室利用率并出一份报告 |

## 2. 业务流程

```
基础数据（学期 / 课程 / 教学班 / 学生 / 教师 / 教室 / 时段）
        ↓
考试计划申报与审核（课程 → 考试时长、期望时段、形式）
        ↓
资源与约束配置（教师可用时段、回避申报、教室停用）
        ↓
自动编排 → 生成方案（可多版本）→ 冲突检测 → 手动调整
        ↓
座位编排（按学号 / 随机）→ 监考分配与负载均衡
        ↓
结果发布 → 学生查询 / 教师监考通知
        ↓
变更（请假 → 替监 → 局部重排）→ 考场情况上报 → 统计报表
```

考试状态机：`DRAFT`（申报）→ `APPROVED`（审核通过）→ `SCHEDULING`（编排中）→ `SCHEDULED`（已编排）→ `PUBLISHED`（已发布）→ `CHANGED`（变更中）。

## 3. 核心算法设计

这一节是整个选题的技术支撑，也是论文第 4 章的内容。

### 3.1 问题建模

**输入**

- 考试集合 `E = {e1…en}`，每场已知：所属教学班、考生集合、时长、可接受时段范围
- 时段集合 `T`（考试周内每天 3 个时段 × 天数）
- 教室集合 `R`，每间有容量与类型；部分教室在部分时段不可用
- 教师集合 `P`，含监考资格、可用时段、回避关系

**冲突图**

以考试为顶点，若两场考试存在共同考生（同班或同学分制班级），则连边。排考的第一步就是给这个图着色，颜色即时段。

**硬约束**

| 编号 | 约束 |
|---|---|
| C1 | 同一考生不能在同一时段参加两场考试 |
| C2 | 同一教室同一时段只能安排一场考试 |
| C3 | 一场考试的考生总数不得超过所分配教室的容量之和 |
| C4 | 同一教师同一时段不能监考两场 |
| C5 | 教师回避的课程或班级不得安排其监考 |
| C6 | 教师未申报可用的时段不得安排其监考 |
| C7 | 考试时长不得超过时段长度 |

**软约束**（目标函数里加权）

| 编号 | 约束 | 权重意义 |
|---|---|---|
| S1 | 监考工作量均衡（各教师场次的标准差） | 公平性 |
| S2 | 同一教师避免连续多个时段监考 | 疲劳 |
| S3 | 教室利用率（容量浪费最小） | 资源 |
| S4 | 学生同一考试日的场次尽量不超 2 场 | 学生体验 |

**目标函数**

```
min f = M × Σ硬违约 + Σ wi × 软成本i
```

其中 `M` 取一个远大于软成本总和的大数，保证任何硬违约都不可接受。

### 3.2 分阶段求解

| 阶段 | 任务 | 方法 | 复杂度 |
|---|---|---|---|
| 1 | 时间分配 | 按冲突度降序的 **DSatur 图着色** | O(n²) |
| 2 | 教室分配 | **首次适应递减（FFD）装箱**，一场考试可拆多间教室 | O(n log n) |
| 3 | 监考分配 | **贪心 + 负载再平衡**：优先可用、无回避、当前负载最低的教师 | O(n·m) |
| 4 | 冲突修复 | **模拟退火**：邻域为「移动考试时段」「交换两场时段」「更换教室」 | 可配置迭代数 |

分阶段而不是一次性求解，是工程上的取舍：全局搜索（如遗传算法）质量可能更好，但不可控、难调试、给教师的解释成本高。分阶段每一步都有明确语义，出了问题能定位到「哪一场、哪一条约束」。

### 3.3 评价指标

| 指标 | 含义 |
|---|---|
| 硬冲突数 | 必须为 0 才能发布 |
| 软成本 | 加权后的 S1–S4 之和 |
| 监考工作量极差 / 标准差 | 越小越均衡 |
| 教室利用率 | 实际使用座位 / 分配教室总容量 |
| 求解耗时 | 用于说明可交互性 |

### 3.4 实验设计（第 6 章素材）

- 规模：100 / 300 / 500 场考试（按本校实际规模设定，参数可配置）
- 对比：纯贪心 · DSatur · DSatur + 装箱 · 全流程（DSatur + FFD + SA）
- 指标：冲突数、软成本、耗时、工作量标准差
- 数据：**模拟生成器**（冲突率、教室容量分布、教师回避比例可调），并说明生成规则与局限性

## 4. 角色与端

| 角色 | 主端 | 职责 | 关键权限 |
|---|---|---|---|
| 教务管理员 | Web 后台 | 基础数据、考试计划审核、编排与调整、发布、统计 | 全部编排操作；可查看冲突与质量报告 |
| 教师 | Web | 查看监考、申报可用时段与回避、请假与替监、签到、情况上报 | 只看自己的监考；不能改他人安排 |
| 学生 | Android（uni-app） | 查看考试安排、考场座位、变更通知、缓考申请 | 只看本人考试 |

角色比前几版更「薄」，但这正是该类系统的真实形态：**系统的重量在算法与管理端，学生端天然是只读的**。工作量不靠学生端堆模块，而靠编排引擎与教务流程。

## 6. 数据模型（37 张）

| 域 | 表 | 说明 |
|---|---|---|
| 账号与权限（7） | `app_user` `auth_session` `role` `user_role` `permission` `role_permission` `user_profile` | 复用现有鉴权，增加角色区分 |
| 组织与人员（4） | `department` `class_info` `student_profile` `teacher_profile` | 院系、班级、学生、教师（含监考资格） |
| 课程与教学（3） | `course` `teaching_class` `teaching_class_student` | 教学班是冲突判定与容量的基本单位 |
| 考试与资源（6） | `semester` `exam_period` `time_slot` `classroom` `classroom_unavailable` `exam` | 时段与教室可达性 |
| 编排（5） | `schedule_plan` `exam_schedule` `exam_room` `seat_assignment` `invigilation_assignment` | 方案版本、考试→时段、考试→教室（可多间）、座位、监考 |
| 规则（3） | `scheduling_rule` `teacher_availability` `teacher_avoidance` | 约束参数与教师申报 |
| 协同流程（4） | `leave_request` `substitute_request` `exam_incident` `makeup_exam` | 请假/替监、现场上报、缓考 |
| 通知与后台（5） | `notification` `operation_log` `sys_config` `import_record` `announcement` | |

两个关键设计：

1. **`exam_room` 单独成表**，允许一场考试拆成多间教室（人数超单间容量），`exam_schedule` 只管考试→时段。这样「拆考场」不会污染编排主表。
2. **`schedule_plan` 存方案版本**，每次自动编排产生一个版本，保留参数快照与质量指标，支持「方案 A 与方案 B 对比」，也支持回滚。

## 11. 答辩口径

**问：排课排考是被研究烂了的经典问题，你的创新点在哪？**

> 不承诺算法理论创新。价值在三处工程实现：一是约束建模完整（含教师回避、可用时段、一场考试拆多间教室，多数简化系统不做）；二是分阶段求解可定位可解释，出问题能指出是哪一场、哪条约束；三是给出量化指标体系与策略对比实验。本科阶段把这三件事做扎实，比声称一个改进算法更实在。

**问：数据从哪来？**

> 模拟生成器，按本校实际规模设定参数（考试数、班级分布、教室容量、教师回避比例），生成规则写进论文，并说明局限：模拟数据无法完全反映真实教务的异常情况。

**问：为什么不用遗传算法一步到位？**

> 已做对比：全局搜索在软成本上可能更优，但不可控、调试成本高、给教务人员的解释成本高。分阶段方案每一步语义清晰，且能在 30 秒内出结果，可交互调整。实验章节会给出对比数据。

**问：教师端和学生端功能很薄，是不是凑数？**

> 这类系统的重量在编排引擎与管理端，学生端天然只读。模块数量不是目标，编排质量才是。
